# GHOSTS scenario document, schema v1

A scenario document is one exercise scenario as a single, versioned, diffable JSON file. It carries
the authored specification: what the exercise is for, who plays, who the adversary is and what it can
do, the terrain, the rules of play, the timeline, the assessment standard, and the entity graph. It
carries no run state and no database identity. Names use the exercise developer's vocabulary;
standards (ATT&CK, CVE, cron) sit at the leaves.

This folder is Step 1 of the agentic scenario authoring plan. The design is the file's authority; the
schema is what the design's Step 1 asks for: the union of what the API's create endpoint accepts and
what the RPG experiment validates, with RPG's preconditions, flags and indicators adopted, the
environment block structured, and the schema versioned from the first commit.

## Rules the schema follows

1. **The exercise developer's vocabulary is the structure.** `audience`, `sides`, `adversaries`,
   `terrain`, `population`, `rulesOfPlay`, `assessment`, `timeline`. The API's table names
   (`scenarioParameters`, `gameMechanics`) do not appear.
2. **Standards at the leaves.** ATT&CK technique ids, CVE ids and cron strings are validated by
   pattern where they appear. The document never restates what the standard says; a validator
   resolves the id.
3. **Not every exercise is a cyber exercise.** Beside each standard leaf is a plain-words neighbour:
   `adversaries[].capabilities[]` next to `techniques[]`, `vulnerabilities[].description` next to
   `cve`, `events[].displayTime` next to `at`. The 1944 OVERLORD fixture needs all three.
4. **No database ids, timestamps or run state.** Entities and objectives use author-chosen local ids.
   Event status, objective score and status, builder status, compilations and source contents are out.
5. **One list of events.** The API keeps injects and timeline events in two collections that nothing
   reconciles. The document has `timeline.events[]` only; an inject is an event with a title.
6. **One duration.** The API stores `durationHours` and `exerciseDuration` separately, with no stated
   unit for the second; the fixtures hold 1 and 60, 0.75 and 90, 1 and 75. The document has
   `rulesOfPlay.duration`.
7. **Nothing is bound silently.** The API seeds three n8n workflow bindings on every scenario with no
   UI. In a document, `workflows[]` lists what is bound, and an absent list binds nothing.
8. **The environment block is structured even though nothing consumes it yet.** `terrain` has
   `segments`, `hosts`, `services`, `defenses`, `vulnerabilities`, a `reference` to a base network in a
   terrain provider, and an `informationEnvironment` for the cognitive side. `terrain.summary` keeps
   the prose of older scenarios so nothing is lost.
9. **Canonical means one serialization per scenario.** Keys in schema order, free-key objects sorted,
   set-like arrays sorted (`flags`, `setFlags`, `techniques`, event `objectives`), empty optional
   values omitted, values equal to their schema `default` omitted, two-space indent, one trailing
   newline. `canonicalize` produces it; the test checks the examples are already in it. Defaults live
   in the schema (from v1.1.0) so that a reader and a writer agree on what an absent field means, and
   an export cannot pad a document with values its author never wrote.

## The document, block by block

| Block | Holds | Required |
|---|---|---|
| `schemaVersion`, `slug`, `name`, `description` | Identity. | yes |
| `intent` | The developer's plain-English brief. The paragraph an authoring agent starts from. | |
| `catalog` | Listing metadata for a picker. | |
| `context` | `political` background (White Cell) and the `situation` briefing shown to the audience. | |
| `audience` | `role`, `size`, `proficiency`, `mandate`, `rulesOfEngagement`. The elicitation-checklist fields. | |
| `sides` | Nations or organizations with `alignment`. | |
| `adversaries[]` | `type`, `capability` 1–5 with defined anchors, `techniques[]`, `capabilities[]`, `objective`, `winThreshold`, `playbook[]` of precondition-gated moves. | |
| `terrain` | See rule 8. | |
| `population.pools[]` | Simulated people: `role`, `count`, `description` of who they are. | |
| `startingConditions` | Initial `flags[]` and `facts{}`. | |
| `rulesOfPlay` | `pacing`, `duration`, `clock`, `deadline`, `adjudication`, `fog`, `telemetry`, `escalationLadder` with `rungs[]`, `branching`. | |
| `assessment` | `purpose`, `victoryConditions`, `performanceMetrics`, `objectives[]` with `metWhen` gates. | |
| `timeline.events[]` | Each fires `at` an offset, on a `schedule`, or `when` a condition holds; has an `owner`, `expectedResponse`, `effects`, `indicators`, `execution`. | |
| `workflows[]` | Automation bound to a run. | |
| `entities[]`, `edges[]` | The graph, with `provenance` on each. | |
| `sources[]`, `references[]` | What the scenario was built from, and citations prose can point at as `[ref:id]`. | |

### Grammar

| Type | Form | Examples |
|---|---|---|
| offset | `T+` then days, hours, minutes in that order, each optional, at least one | `T+10m`, `T+2d9h40m`, `T+0m` |
| duration | days, hours, minutes in that order, each optional, at least one | `11d`, `1h`, `45m`, `1h30m` |
| condition | terms joined by `&&`: `flag:<flag>`, `!<flag>`, `objective:<id>`, `clock>=<minutes>`; empty is always true | `flag:has-foothold && !host-isolated` |

The condition grammar is the RPG engine's, unchanged: an unknown term makes the whole condition
false, never true. The offset form extends the API's existing `T+10m` convention with `d` and `h` so
an eleven-day exercise can say `T+2d9h40m` instead of `T+57h40m`.

### What the API cannot hold

Step 2's export and import (`GET /api/scenarios/{id}/document`, `POST /api/scenarios/import`) map
everything the tables above list. These blocks have no column, so an import accepts them, a reader
can still diff them, and an export cannot emit them:

| Document | Why |
|---|---|
| `slug` | No column. An export derives it from the name, so a document's own slug does not survive. |
| `intent`, `catalog` | No columns. |
| `audience.role`, `size`, `proficiency`, `mandate` | Only `rulesOfEngagement` has a column. |
| `adversaries[].objective`, `winThreshold`, `playbook[]` | The RPG keeps these in its own bundle. |
| `terrain.reference`, `segments[]`, `hosts[]`, `services[]`, `informationEnvironment` | `technicalEnvironment` holds three prose columns and a defense list. |
| `terrain.defenses[].description`, `covers`; `population.pools[].description` | Only the name and the count have columns. |
| `startingConditions` | No columns. |
| `rulesOfPlay.clock`, `deadline`, `fog`; `escalationLadder.rungs[]` | No columns. |
| `assessment.objectives[].metWhen` | No column. |
| `timeline.events[].id`, `title` with a description, `expectedResponse`, `effects`, `indicators` | The event row has `number` and one description. An event id is rebuilt as `event-{number}`. |
| `sources[]`, `references[]` | Builder sources hold uploaded content, which a document must not carry; nothing else stores a citation. |
| `entities[].provenance` absent | The columns have defaults (`Operator`, confidence 1, not reviewed), so an export always states provenance even where the document did not. |
| a sub-hour or non-integral `duration` | `durationHours` is an integer. An import refuses the document (`TIME_DURATION_NOT_STORABLE`) rather than rounding it, so `45m` does not come back wrong — it does not go in at all. |

## The four fixtures, expressed

`tools/test.sh` converts each fixture, checks that every source value survives, and validates the
result. All four pass. The converter reports what it had to decide:

| Fixture | Shape | Result | Notes |
|---|---|---|---|
| `phishing-drill` | API | 104/104 values kept, valid | |
| `soc-morning` | API | 111/111, valid | `exerciseDuration` 90 vs `durationHours` 0.75; document says `45m` |
| `operation-overlord` | API | 120/120, valid | 4 of 4 "TTPs" are prose → `capabilities[]`; 2 of 2 "CVEs" are prose → `description`; times are wall-clock → `displayTime`; `exerciseDuration` 75 vs `durationHours` 1 |
| `meridian-hybrid` | RPG | 82/82, valid | |

Two things the fixtures show about the current data model. The two duration fields cannot both be
in hours (1 and 60, 0.75 and 90, 1 and 75), and the prose in OVERLORD's `ttps` and `cve` fields
would fail any validator that took those field names at their word. Both are arguments for the document's typed
leaves with plain-words neighbours.

## Standards considered

A desk evaluation against the published specifications, not a test against a parser. Each was
checked for one question: could it be the container for a whole exercise, or a leaf inside one?

| Standard | Covers | Verdict for v1 |
|---|---|---|
| **STIX 2.1** | Threat actors, intrusion sets, indicators, attack patterns, vulnerabilities, infrastructure | Leaf, not container. Every STIX object carries `created`/`modified` timestamps and a `type--uuid` id, which conflicts with a canonical, id-free document. ATT&CK ids are STIX-backed already. `entities[].externalId` may hold a STIX id. |
| **MITRE Attack Flow** | Sequences of techniques with conditions and operators, as a STIX extension | Closest to `adversaries[].playbook[]`, and a natural **export target** later. Not adopted as the authoring form: its conditions are free text, it has no flag or effect semantics a runtime can gate on, and its graph-of-references form is not hand-authorable in a developer's vocabulary. |
| **OASIS CACAO 2.0** | Response playbooks: workflow steps, agents, targets, commands | Not needed in v1. The audience's responses are free at runtime, not scripted. A candidate for scripted White Cell responses or for describing what an n8n workflow binding does. |
| **HSEEP MSEL** (convention, not a schema) | Inject number, time, from, to, description, expected action | Adopted in spirit: `timeline.events[]` has `owner`, `objectives`, and `expectedResponse`, the column the API's event lacks. |
| **ISO 8601 durations** | `P11D`, `PT10M` | Not adopted. Exercise developers say "day 2, 09:40"; the existing `T+10m` convention was kept and extended. |

## Versioning

`schemaVersion` is semantic. A patch adds nothing a reader must understand. A minor version adds
optional fields. A major version changes or removes a field, and an older reader must refuse the
file rather than read it wrong. The `$id` carries the version. The regression suite is the four
fixtures plus every scenario the Step 2 round-trip test exports.

v1.1.0 declares the defaults listed in rule 9 and requires a `description` on an event that carries
`when`, `schedule`, `objectives` or `execution`. The API accepts both versions and validates both
against the 1.1.0 schema, which is a compromise worth naming: declaring defaults is a minor change,
but requiring the description can reject a document 1.0.0 accepted. It was taken as minor because such
an event becomes an Inject row and silently loses `when`, `schedule`, `objectives` and `execution` —
being told is better than being imported wrong — and because no document of that shape exists outside
`tests/invalid.scenario.json`.

## Open questions for the GHOSTS team

1. **Where does the schema live in the repository?** This folder is written to land as
   `schemas/scenario-document/` at the repository root, because the API (validator, Step 3), the RPG
   (Python), and an authoring agent all read it. `src/Ghosts.Api/` would tie it to one consumer.
2. **Entity and edge types.** The API comments list a vocabulary but the column is a free string, and
   the fixtures already use `Resource`, `Defends`, `Enables` and `PlansFor`, which are not in the
   list. The schema keeps the string free and lists the recommended vocabulary. Should v1 close it?
3. **Enrichments.** The builder caches ATT&CK and CVE detail as enrichment rows. The document holds
   the ids and not the cached detail, on the argument that the detail is the standard's, not the
   scenario's. A fully offline load would then need the corpus (Step 3a) present. Is that acceptable?
4. **Objective status and score** are dropped as run state. If a scenario is authored with some
   objectives already `Active`, that is lost. Is lifecycle status authored or operated?
5. **The two duration fields.** The document keeps one. When Step 2's export reads the API, which of
   `durationHours` and `exerciseDuration` is the truth, and in which unit? Step 2 answers
   provisionally: the export reads `durationHours` as hours, and an import writes both columns in
   hours from the document's one duration so they cannot disagree again. That leaves two questions
   for the team — whether anything relies on `exerciseDuration` being minutes, and whether
   `durationHours` should become minutes so sub-hour exercises survive.

   Step 3 sharpens this. `GameMechanics.DurationHours` is an `int`, so a sub-hour exercise cannot be
   stored, and two of the four reference fixtures are sub-hour: `soc-morning` is
   `durationHours: 0.75` and `meridian-hybrid` a 90-minute window. Import refuses a duration it
   cannot store rather than rounding it (`TIME_DURATION_NOT_STORABLE`), so those two examples say
   `45m` and `1h30m`, exactly as their fixtures do, and are **not importable** until the column holds
   minutes. The converter prints a note saying so. Bending the examples to the column instead would
   have made them an argument that integer hours is enough, and would have weakened Step 1's
   done-when from *expressed* to *importable*. `roundtrip.sh` expects the refusal, and the validator
   test names it per file. Until there is a minutes column, an exercise measured in minutes can be
   authored and validated in GHOSTS but not stored.

6. **Threat-actor capability.** The schema allows 1–5 and so does the wizard's input, but
   `config/SeedData/seed.json` ships scenarios with 6, 7 and 9, so six of the nine scenarios in a
   stock database cannot be expressed as valid documents. Is the scale 1–5, and is the seed data
   wrong? Step 3 confirms this is their *only* defect: clamp capability to 5 and all six validate
   clean through both tiers.

7. **Who raises a flag the document only reads?** A branch like `flag:contained` / `!contained` is
   how an exercise asks "did the team contain it?", and three of the four examples write one, but the
   grammar has no way to say that the white cell raises `contained` during play. Step 3's validator
   therefore reports a flag that is read and never set as a warning, not an error — it cannot tell
   that case from a typo. Should an event or an objective be able to declare that it raises a flag on
   adjudication, or should the document list its adjudicated flags?

8. **How is an adversary bound to its entity?** The examples give an adversary the same slug as the
   `ThreatActor` entity that represents it, which is the only binding available, so the validator
   exempts that one pair from its uniqueness check. An explicit `entityRef` on the adversary would
   say it out loud. Which does the team want?

9. **The compile path drops the timeline.** A dry run of `phishing-drill` loads 8 timeline events and
   1 inject and then compiles to 0 timeline events and 0 injects (`meridian-hybrid`: 2 events in, 0
   out). Either compilation is expected to ignore the authored timeline, or something in it does not
   survive `ScenarioCompilerService`. This was found by tier 4 and not investigated.

10. **Who keeps the ATT&CK index current?** `corpus/attack-index.json` names the
    `mitre-attack/attack-stix-data` commit it was built from. It is a committed artefact with no
    refresh job, so a technique revoked after that commit still validates. How often, and by what,
    should it be rebuilt?
